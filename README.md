# 概要
このリポジトリは私が初めてリリースしたゲーム **「Extinguishing Contract」** のUnityプロジェクトとなります。  
ゲーム自体の情報に関しては、下記の情報一覧をご覧ください。

# 全体構造
本作では主に **「シーン間の完全な疎結合」** を達成することが設計における目標となりました。  
そのため本作の構造は、以下の思想を基に構築されています。  
**「一つの大きなデータベースに集約された情報を、各シーンが自由に閲覧して解釈する」**  
**「各シーンは自身の担当範囲に自分の解釈で情報を書き込む。」**  
**「情報ごとに解釈を設計時に統一する」**  
これによりシーン間の通信が消滅したため、シーンごとにロジックを制作することが可能となりました。  
また、ダミーのデータを用いたテストや、シーン単体での動作確認がスムーズに行えるようになり、開発効率の向上に大きく寄与しました。

# データ構造
本作では、データは**マスターデータ**、**セーブデータ**、**シーンデータ**の三種類に分類されます。  
### マスターデータ
本作におけるマスターデータとは、 **「制作者によって制作時に完全に決定され、プレイ時に書き換わる事が無いデータ」** を指します。  
企画時にゲームの仕様をほぼ決定していたため、マスターデータに必要な要素の種類が自ずと確定。結果として、Config、ユニット、マップ、指標といったように種類ごとにデータベースを作り、中の要素は配列で保持することで拡張性を確保する設計となりました。  
一方で、制作の後半においては、主にConfigといった中の要素まで確定していたデータベースとインデックス参照との相性の悪さにより、少なからずストレスを感じる結果にもなりました。
### セーブデータ
本作におけるセーブデータとは、 **「起動時に構造は確定しているが、中のデータはプレイによって書き換わり、ゲームを閉じても情報が失われないデータ」** を指します。  
こちらも企画時にゲームの仕様が決定していた恩恵を受け、最初から必要な種類が確定。  
起動時にマスターデータを参照して種類ごとの要素数を確定し、staticメンバーとしてゲームを通して保持することで、全シーンがいつでも参照・書き込みできるような状況を作り出しました。  
書き込みの担当領域に関しては、仕組みとして領域外へ書き込むことを阻止するような設計はしておらず、事前の設計図頼りとなっています。
### シーンデータ
本作におけるシーンデータとは、 **「各シーンで保持し、そのシーン内でのみ使われるデータ」** を指します。
言葉通りであり、シーンが切り替わるとそのまま破棄されます。

# その他
### カプセル化について
本作では採用しませんでした。  
理由としては、本作はゲームとして、個々のインスタンスが自立して動くというよりは、コンソールを介してデータベースを操作するようなものに近かったため、カプセル化のためのインスタンス自体を生成する必要が無かったためです。
### パフォーマンスについて
本作は、理論上では最も処理が重くなる消火活動シーンにおいても全ての処理がスタックで完結するほか、UI Toolkitによるドローコールの少なさも重なり、動作が非常に軽くなっています。  
ですが、制作者としては、意識しなかったといえば噓になりますが、基本的には自身がコードを書きやすいようにデータ構造を調整したりした結果の副産物と見ています。  
理屈としては、怠惰ゆえに同じことを何度も書きたくなかったため、for文でまとめて回せるように各データをインデックスで貫くようなデータ構造を採用した結果、データが配列の形となりキャッシュ効率が向上。さらに配列故Span<T>とstackallocが使用可能になった結果、処理がスタック領域で完結するように。結果GCの稼働が減りカクつきが減少、といったところでしょうか。
### Zero Allocationについて
特にStageSceneやUnitSceneで顕著ですが、本作では起動時に必要な領域を一括で確保し、その後の動的な確保をしないコードが多用されています。  
ですがこれは単なる制作者の美意識とこだわりによるものであり、パフォーマンス向上を企図したものではありません。
